# 신규 매장 승인 후 생성 (#840)

2026-10-08 사용자 확정: 매장 선택 안내를 표시하고, 승인 전에는 별도 요청만 보관한다. 관리자 승인 후 정식 매장 DB에 추가한다.

## 저장 계약

- 신규 매장: `stage_user_place_item`은 `private.user_place_requests` + pending item + 지도 채널만 만든다. `register_item_pick`의 needs_review Pick·사진·한줄평 계약은 유지한다.
- 승인 전 `places`, `place_catalog`, `providers`, `item_places` 행은 만들지 않는다.
- MFA 관리자 승인 함수가 요청을 정식 매장으로 전환하고 기존 항목·원픽을 공개한다. 같은 이름+정확히 같은 지도 링크의 정식 매장은 재사용한다. 같은 매장×메뉴가 이미 연결되어 있으면 승인 전체를 롤백한다.
- 반려는 요청을 유지한다. 링크 수정은 요청 정보에 반영되며 기존 요청/정식 매장과 충돌하는 링크 변경을 거부한다.
- private 요청 테이블은 RLS를 켜고 anon/authenticated 직접 권한을 주지 않는다. 공개 RPC의 기존 인증·소유권·MFA 검사를 유지한다.
- 기존 hidden 매장은 삭제하거나 대량 이관하지 않는다. 기존 사용자 데이터를 손상시키지 않고 새 요청부터 정책을 적용한다.

## #839 통합 조건

#839의 `unclassified_menu_place`는 현재 hidden places/catalog를 먼저 만든다. #840과 함께 운영 적용하려면 미분류 메뉴의 신규 매장 경로도 이 요청 구조를 사용해야 한다. 미분류 메뉴의 기존 매장은 기존 place_id를 유지하고, 신규 매장만 요청 메타데이터로 보관한다. 관리자 분류 후 유효한 메뉴 category_id를 얻은 다음 정식 매장을 생성해야 한다. #839 브랜치를 이 작업에서 직접 수정하지 않으며 #836에 작업 경계를 기록한다.

## 배포와 검증

1. 현재 main 경로의 Mobile/DB/locked-contracts CI와 Claude DB 독립 리뷰.
2. #839 미분류 경로 통합 검증. 통합 전 두 변경을 함께 운영 완료로 보고하지 않는다.
3. 사용자 main 병합 승인. 이전 #835 승인은 이 신규 DB 변경의 승인으로 사용하지 않는다.
4. DB 배포 dry-run → 사용자 Production apply 승인 → 운영 적용.
5. QA 일반 계정으로 제출 후 승인 전 정식 매장 0건, 별도 요청 1건 확인. MFA 관리자가 승인한 후 정식 매장 1건과 기존 원픽/사진/한줄평 유지 확인. 반려/재신청/중복 승인도 검사한다.

운영 DB는 이 PR 작성 중 변경하지 않는다. 앱의 선택 안내는 DB 적용과 별개이며 저장 RPC 서명은 유지된다.
