# 접속·이동 로딩 시간 개선

## 확인한 지연 경로

- 테스트 사이트(`onepick-5cl.pages.dev`)의 `_headers`가 `https://:project.pages.dev/*`와
  미리보기 주소 전체에 `Cache-Control: no-store, max-age=0`을 적용했다. 검색 엔진
  수집을 막으려는 `X-Robots-Tag: noindex`와 같은 블록에 있었지만, 실제로는 파일
  이름에 콘텐츠 해시가 들어간 JS·CSS·이미지에까지 적용되어 **매 접속마다 번들
  전체를 다시 내려받았다**. 현재 내보내기 기준 진입 번들은 단일 파일
  3.16MB(gzip 732KB)다.
- 홈 첫 화면의 읽기가 직렬로 이어졌다. 세션 확인 → 카테고리 목록 → (내 원픽 ·
  사람들의 원픽 피드 · 추천 원픽) → 브라우즈 카테고리 목록 순서였고, 뒤의 세
  단계는 서로 필요로 하지 않는데도 앞 단계를 기다렸다.
- 홈 피드의 다음 페이지도 카테고리·내 원픽·추천 원픽을 매번 다시 읽었다. 화면은
  첫 페이지의 값만 사용하므로 읽은 결과는 그대로 버려졌다.
- 카테고리 목록이 기본 신선도 30초를 따라 홈 → 탐색 → 프로필 이동마다 같은 행을
  다시 요청했다.
- 사용하지 않는 조회 결과를 5분 만에 버려서, 상세 화면에 머물다 돌아오면 이미
  받아 둔 목록이 사라지고 빈 로딩 화면이 다시 보였다.

## 변경

- `public/_headers`에서 Pages 호스트의 `Cache-Control: no-store`를 없애고,
  콘텐츠 해시가 붙는 `/_expo/static/*`와 `/assets/*`에만
  `Cache-Control: public, max-age=31536000, immutable`을 준다. `noindex`는 그대로
  둔다. Cloudflare Pages는 일치하는 규칙들의 헤더 값을 **쉼표로 이어 붙이고**
  나중 규칙이 앞 규칙을 덮지 않으므로, 두 해시 경로 외에는 어떤 규칙도
  `Cache-Control`을 선언하지 않는다. `index.html`을 포함한 나머지는 Pages 기본값
  `public, max-age=0, must-revalidate`와 ETag를 그대로 써서 매번 재검증하며, 지난
  배포의 HTML이 남는 경로를 만들지 않는다.
- `HomeService.getHomeData`가 카테고리 목록을 먼저 기다리지 않고 네 건의 읽기를
  한 번에 보낸다. 홈 첫 화면의 직렬 요청 단계가 세션 확인 이후 **3단계에서
  1단계로** 줄어든다.
- 커서가 있는 홈 다음 페이지는 피드 한 건만 읽는다(요청 4건 → 1건). 첫 페이지의
  카테고리·내 원픽·추천 원픽은 홈 조회가 그대로 유지한다.
- 홈 화면이 브라우즈 카테고리 목록을 피드 도착 후가 아니라 화면 진입과 동시에
  요청한다. 이 목록은 공개 데이터이며 모든 사용자에게 같다.
- 브라우즈 카테고리 조회의 신선도를 30초 → 10분으로 둔다. 카테고리는 Admin
  편집으로만 바뀌고, 기존 Admin 변경은 이미 `queryKeys.categories`를 무효화하므로
  편집 결과는 즉시 다시 읽는다.
- 사용하지 않는 조회 결과 보관 시간을 5분 → 30분으로 둔다. 돌아왔을 때 받아 둔
  내용을 즉시 그리고 갱신은 뒤에서 진행한다. 신선도(30초)는 바꾸지 않는다.
- 검색 SQL, 순위, 인덱스, 검색 입력 대기(150/200ms), 공개 범위, 인증 설정,
  의존성은 바꾸지 않는다. 화면에 보이는 내용과 권한 규칙도 그대로다.

## 검증

- `test-startup-loading.cjs`: 홈 화면이 카테고리 목록을 다른 조회 뒤로 미루지
  않는지, 카테고리 신선도와 결과 보관 시간 설정, Admin 편집의 무효화가 남아
  있는지, `_headers`의 해시 경로 캐시 규칙과 `no-store` 부재를 검사한다.
- `test-home.cjs`: 카테고리 목록을 **피드 요청이 시작된 뒤에만** 응답하는
  저장소로 홈을 불러, 순차로 읽던 구현이면 통과할 수 없게 했다. 다음 페이지가
  피드만 읽는지, 첫 페이지의 카테고리·내 원픽을 그대로 두는지도 함께 검사한다.
- `check-web-export.cjs`(CI `verify-web`): 내보낸 `_headers`를 규칙 단위로 읽어
  `Cache-Control`을 선언하는 규칙이 두 해시 경로뿐인지, `index.html`이 그 경로에
  들어가지 않는지, `index.html`이 실제로 참조하는 JS·CSS가 모두 장기 캐시 경로
  아래에 있는지 확인한다. 내보내기 경로가 바뀌면 캐시가 조용히 사라지지 않고
  검사에서 걸린다.
- `npm run typecheck`, `npm test`, `npm run build:web && npm run check:web`을
  이 브랜치에서 실행했다.

## 측정 경계와 배포

- 위 숫자는 **요청 횟수와 설정값**이며 실기기·실네트워크 실측이 아니다. 확정할
  수 있는 것은 홈 첫 화면의 직렬 단계 3 → 1, 다음 페이지 요청 4 → 1, 재방문 시
  해시 자산 재다운로드 없음, 화면 이동 시 카테고리 재요청 없음이다.
- 실제 체감은 배포 후 같은 휴대폰·네트워크에서 첫 접속, 재접속, 탭 이동, 검색의
  p50/p95를 비교해야 한다. 캐시 효과는 두 번째 접속부터 나타난다.
- 검색 자체의 서버 시간은 이번에 건드리지 않았다. 검색 로딩이 남는다면 다음
  후보를 따로 확인한다.
  - `search_items`가 후보 행마다 `category_is_open_leaf`(재귀 CTE)를 호출한다.
  - 진입 번들이 코드 분할 없는 단일 3.16MB 파일이다(`web.output: "single"`).
  - 검색 결과 썸네일의 첫 이미지 로딩과 외부 카탈로그(TMDB 등) 첫 호출.
- 홈은 이제 `categories` 행을 두 경로로 **동시에** 읽는다(홈 조회 안의 선택 가능
  카테고리, 화면의 브라우즈 카테고리). 순차가 아니라 지연에는 영향이 없지만,
  `getOpenCategories`가 `getBrowseCategories` 결과의 순수 변환이므로 화면에서
  한 번만 읽도록 합치는 정리가 남아 있다.
- `main`, Cloudflare/Vercel 배포 설정, 운영 DB·마이그레이션·사용자 데이터, 인증
  설정은 바꾸지 않는다.
