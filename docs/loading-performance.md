# 접속·이동 로딩 시간 개선

## 확인한 지연 경로

- 테스트 사이트(`onepick-5cl.pages.dev`)의 `_headers`가 `https://:project.pages.dev/*`와
  미리보기 주소 전체에 `Cache-Control: no-store, max-age=0`을 적용했다. 검색 엔진
  수집을 막으려는 `X-Robots-Tag: noindex`와 같은 블록에 있었지만, 실제로는 파일
  이름에 콘텐츠 해시가 들어간 JS·CSS·이미지에까지 적용되어 **매 접속마다 번들
  전체를 다시 내려받았다**. 현재 내보내기 기준 진입 번들은 단일 파일
  3.16MB(gzip 732KB)다.
- 홈 첫 화면의 읽기가 직렬로 이어졌다. 세션 확인 → 카테고리 목록 → (내 원픽 ·
  사람들의 원픽 피드 · 추천 원픽) → 브라우즈 카테고리 목록 순서였고, 뒤의 세
  단계는 서로 필요로 하지 않는데도 앞 단계를 기다렸다.
- 홈 피드의 다음 페이지도 카테고리·내 원픽·추천 원픽을 매번 다시 읽었다. 화면은
  첫 페이지의 값만 사용하므로 읽은 결과는 그대로 버려졌다.
- 카테고리 목록이 기본 신선도 30초를 따라 홈 → 탐색 → 프로필 이동마다 같은 행을
  다시 요청했다.
- 사용하지 않는 조회 결과를 5분 만에 버려서, 상세 화면에 머물다 돌아오면 이미
  받아 둔 목록이 사라지고 빈 로딩 화면이 다시 보였다.

## 변경

- `public/_headers`에서 Pages 호스트의 `Cache-Control: no-store`를 없애고,
  콘텐츠 해시가 붙는 `/_expo/static/*`와 `/assets/*`에만
  `Cache-Control: public, max-age=31536000, immutable`을 준다. `noindex`는 그대로
  둔다. Cloudflare Pages는 일치하는 규칙들의 헤더 값을 **쉼표로 이어 붙이고**
  나중 규칙이 앞 규칙을 덮지 않으므로, 두 해시 경로 외에는 어떤 규칙도
  `Cache-Control`을 선언하지 않는다. `index.html`을 포함한 나머지는 Pages 기본값
  `public, max-age=0, must-revalidate`와 ETag를 그대로 써서 매번 재검증하며, 지난
  배포의 HTML이 남는 경로를 만들지 않는다.
- `HomeService.getHomeData`가 카테고리 목록을 먼저 기다리지 않고 네 건의 읽기를
  한 번에 보낸다. 홈 첫 화면의 직렬 요청 단계가 세션 확인 이후 **3단계에서
  1단계로** 줄어든다.
- 커서가 있는 홈 다음 페이지는 피드 한 건만 읽는다(요청 4건 → 1건). 첫 페이지의
  카테고리·내 원픽·추천 원픽은 홈 조회가 그대로 유지한다.
- 홈 화면이 브라우즈 카테고리 목록을 피드 도착 후가 아니라 화면 진입과 동시에
  요청한다. 이 목록은 공개 데이터이며 모든 사용자에게 같다.
- 브라우즈 카테고리 조회의 신선도를 30초 → 10분으로 둔다. 카테고리는 Admin
  편집으로만 바뀌고, 기존 Admin 변경은 이미 `queryKeys.categories`를 무효화하므로
  편집 결과는 즉시 다시 읽는다.
- 사용하지 않는 조회 결과 보관 시간을 5분 → 30분으로 둔다. 돌아왔을 때 받아 둔
  내용을 즉시 그리고 갱신은 뒤에서 진행한다. 신선도(30초)는 바꾸지 않는다.
- 이 단계에서는 검색 SQL과 인덱스를 건드리지 않는다(3차에서 실행 계획만 바꾼다).
  검색 순위, 검색 입력 대기(150/200ms), 공개 범위, 인증 설정, 의존성도 그대로다.
  화면에 보이는 내용과 권한 규칙은 어느 단계에서도 바뀌지 않는다.

## 2차: 웹 번들에서 쓰지 않는 의존성 제거와 남은 직렬 요청

소스맵(`expo export --source-maps`)으로 번들 구성을 실제로 확인한 결과다.

- **`react-native-reanimated`가 웹 번들 소스의 13%(741KB)를 차지하는데, 웹에서
  이 라이브러리에 닿는 모듈은 `animated-icon.web.tsx` 하나뿐이었다.** 그 파일의
  `AnimatedSplashOverlay`는 웹에서 `null`을 반환하고, 라이브러리를 실제로 쓰는
  `AnimatedIcon`은 Expo 템플릿 잔재로 앱 어디에서도 쓰이지 않았다. 함께 남아
  있던 `ui/collapsible.tsx`(참조 0), `web-badge.tsx`(참조 0), `logo-glow.png`
  (331KB), `expo-logo.png`, `expo-badge*.png`, `animated-icon.module.css`도
  같은 잔재다. 모두 제거했다. **네이티브의 스플래시 연출(`animated-icon.tsx`)은
  그대로 두었고, 웹은 원래 아무것도 그리지 않았으므로 화면 변화가 없다.**
  - 진입 번들 **3,163,792B → 2,353,172B (−25.6%)**, gzip **732,349B →
    586,294B (−20.0%)**, 내보내기 전체 3.6MB → 2.5MB.
- 상품 상세는 피드 카드가 여는 화면이고 원픽 공유 링크의 착지점이다. 카테고리
  행과 내 현재 원픽만 상품 행을 필요로 하는데 나머지도 그 뒤에 줄을 섰다.
  상품 행·리뷰 목록·선택 가능 카테고리·공유 링크가 가리키는 원픽을 한 번에
  읽는다. **직렬 단계 최대 4 → 3**, 로그아웃 상태의 공유 링크는 **3~4 → 2**다.
- `ProfileService.getMyProfile`의 두 읽기는 같은 사용자 ID만 쓰는데 순차였다.
  한 번에 보낸다(**2 → 1**).
- 공개 프로필 `/u/[username]`도 카테고리 목록을 프로필 도착 뒤로 미루고 있었다.
  홈과 같게 동시에 요청한다(**2 → 1**).

## 3차: 검색 SQL이 trigram 인덱스를 쓰게 만들기

`EXPLAIN (ANALYZE)`로 확인한 실제 실행 계획이다. 기존 `search_items`는
`normalized_name`(trigram GIN으로 좁힐 수 있는 조건)과 `item_aliases`를 도는
`left join lateral`의 결과를 하나의 `OR`로 묶었다. 이 형태는 인덱스로 답할 수
없어서, 플래너가 **카테고리에서 출발해 열린 말단 카테고리 안의 모든 상품을
끌어온 뒤(20k 카탈로그에서 12,161행) 각 행마다 별칭 lateral을 돌리고, 그
다음에야** 이름/별칭 조건을 적용했다. 그 중 10,783행이 일을 다 한 뒤 버려졌다.

두 번째 비용은 `category_is_open_leaf`다. 카테고리 트리를 재귀 CTE로 올라가는
함수라 호출당 약 88µs인데, 행마다 호출되면 그것만으로 수백 ms가 된다.

`20260921120000_speed_up_item_search.sql`은 **순위식·가시성 규칙·별칭 처리·
limit·반환 행을 그대로 두고** 도달 방식만 바꾼다.

1. `candidates`가 이름 인덱스와 별칭 인덱스에서 각각 후보 id를 모은다. 순위
   단계가 남길 수 있는 행의 상위집합이다(아래 별칭 조건들은 모두 여기 조건보다
   좁고, 이름 조건은 동일하다). 기존 WHERE 절을 뒤에서 그대로 다시 적용하므로
   자격 없는 후보는 여전히 탈락한다.
2. `category_is_open_leaf`를 **후보가 실제로 쓰는 카테고리마다 한 번씩만**
   호출한다. `materialized` CTE 두 개가 `distinct`를 먼저 계산하도록 보장한다.
   기존(카테고리 테이블 전체에 한 번씩)보다 호출 수가 늘어나는 경우는 없다.

- 측정: 같은 스키마·데이터의 로컬 PostgreSQL 16, 상품 10만 건 기준 일반 검색어
  **평균 410ms → 50ms (8.1배)**. 2만 건에서는 87ms → 24ms (3.6배).
- 1~2글자 검색어는 쓸 수 있는 trigram이 없어 양쪽 모두 스캔한다(10만 건에서
  ~350ms). 이번 마이그레이션으로 달라지지 않는다.

### 이 재작성을 어떻게 검증했는가

- 이 컨테이너에는 Docker가 없어 `supabase db start`를 쓸 수 없다. 대신 로컬
  PostgreSQL 16을 띄우고 `items` / `item_aliases` / `categories`와 두 trigram
  GIN 인덱스를 만든 뒤, **마이그레이션에서 그대로 추출한 실제
  `category_is_open_leaf`와 기존 `search_items`** 를 올려 비교했다.
- 기존 함수와 새 함수의 결과가 **완전히 같은지**를 확인했다: 한국어/영어/접두사/
  오타/숫자/1글자/공백/`null` 26개 검색어의 **순서까지 동일한 id 배열**, 카테고리
  범위·`limit` 1/5/20/50/200·연속 공백 입력 10개 조합, 그리고 전체 행 집합
  (`except all` 양방향) 비교.
- 별칭으로만 닿는 행(정확·접두사·부분·유사도), 카테고리를 닫았을 때 사라지는지,
  상품이 `pending`이 되면 사라지는지, 빈 카테고리 범위가 비는지도 확인했다.
- 기존 `025_search_visibility.sql`의 단언들을 같은 복제본에서 그대로 재생해
  통과하는 것을 확인했다(역할/RLS 부분 제외).
- 다만 **025만으로는 이번 재작성의 핵심 위험을 잡지 못한다.** 별칭 union 절반을
  지운 고장 버전을 만들어 돌려 보니 025는 그대로 통과했다. 025의 별칭 검색어가
  상품 이름과 같은 토큰으로 시작해서, 별칭 경로가 막혀도 이름 경로로 찾아지기
  때문이다. 그래서 `supabase/tests/039_search_candidate_set.sql`을 추가했다.
  검색어와 trigram을 하나도 공유하지 않는 이름을 가진 상품을 별칭으로만 찾게
  해서 별칭 경로를 고립시키고, 그 행에도 카테고리·상품 가시성 규칙이 그대로
  적용되는지 확인한다. 같은 고장 버전에서 실제로 실패하는 것을 확인했다.
- **RLS와 실제 운영 스키마 전체는 이 복제본에 없다.** 가시성 계약의 최종 검증은
  CI `database-tests`가 도는 `025`(익명/로그인 호출자와 RLS 포함)와 새 `039`이다.
  마이그레이션은 병합 후 `supabase db push`로 직접 적용해야 사이트와 DB가
  일치한다.

## 측정 경계와 배포

- 위 숫자 중 번들 크기만 실측값이고, 나머지는 **요청 횟수와 설정값**이며
  실기기·실네트워크 실측이 아니다. 확정할 수 있는 것은 홈 첫 화면의 직렬 단계
  3 → 1, 홈 다음 페이지 요청 4 → 1, 상품 상세 4 → 3(공유 링크 2), 내 프로필
  2 → 1, 공개 프로필 2 → 1, 재방문 시 해시 자산 재다운로드 없음, 화면 이동 시
  카테고리 재요청 없음이다.
- 실제 체감은 배포 후 같은 휴대폰·네트워크에서 첫 접속, 재접속, 탭 이동, 검색의
  p50/p95를 비교해야 한다. 캐시 효과는 두 번째 접속부터 나타난다.
- 검색 SQL의 8.1배는 **합성 데이터를 올린 로컬 PostgreSQL 16의 실측**이지 운영
  DB의 실측이 아니다. 실제 이득은 현재 카탈로그 규모에 달려 있다. 상품이 적으면
  차이가 작고, 늘어날수록 커진다(기존 구조는 상품 수에 비례해 느려졌다).

## 아직 남은 것

- 진입 번들은 여전히 코드 분할 없는 단일 파일이다(`web.output: "single"`).
  Admin 화면과 외부 카탈로그 화면까지 모든 방문자가 내려받는다.
- 홈은 `categories` 행을 두 경로로 **동시에** 읽는다(홈 조회 안의 선택 가능
  카테고리, 화면의 브라우즈 카테고리). 순차가 아니라 지연에는 영향이 없지만,
  `getOpenCategories`가 `getBrowseCategories` 결과의 순수 변환이므로 화면에서
  한 번만 읽도록 합치는 정리가 남아 있다.
- 프로필 탭의 기록·요청 목록이 프로필 도착 뒤로 묶여 있다(직렬 2단계). 사용자
  ID만 있으면 읽을 수 있으나, 프로필이 없는 온보딩 상태에서 빈 요청 2건이
  더 나가므로 이득과 맞바꿀지 판단이 필요하다.
- 세션 확인이 모든 첫 요청 앞에 있다. 홈 피드는 서버가 `auth.uid()`로
  자기/차단 제외를 적용하는 뷰어별 내용이라, 세션 전에 먼저 쏘면 익명 결과를
  받았다가 다시 읽어야 한다. 토큰 갱신이 필요한 재방문에서만 한 번의 왕복이
  더해지는 구조다.
- 검색 결과 썸네일의 첫 이미지 로딩과 외부 카탈로그(TMDB 등) 첫 호출.
- `main`, Cloudflare/Vercel 배포 설정, 운영 DB·마이그레이션·사용자 데이터, 인증
  설정은 바꾸지 않는다.
