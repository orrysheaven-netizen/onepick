# 프로필 사진 배포·복구 절차

대상: DB PR #737, 앱 PR #739. 기존 프로필 개편 #826과 앱 통합 후 진행합니다.
운영 변경과 main 병합은 사용자 승인 후 별도 수행합니다.

## 배포 순서

1. 새 DB head의 필수 CI, Claude DB/RLS 재리뷰, 두 세션 동시 업로드 검증을 확인합니다.
2. Deploy Database Migrations dry-run으로 `20261008071911_add_profile_images.sql`이 한 번만 적용될 예정인지 확인합니다. 구 버전 `20261005100000`이 원격에 이미 적용됐으면 **중단**하고 migration history와 실제 스키마를 대조합니다. 번호를 강제로 repair하지 않습니다.
3. 사용자 운영 승인 후 DB migration을 적용합니다. 버킷(JPEG, 1 MiB), RPC, INSERT/SELECT/DELETE 정책, 정지 사용자 업로드 차단을 확인합니다.
4. `delete-account` Edge Function을 배포하고 배포 버전/결과를 기록합니다. 이 함수는 버킷이 없는 환경에 먼저 배포하지 않습니다.
5. 전용 QA 일반 계정으로 사진 설정·변경·해제 및 별도 승인된 QA 계정 삭제 검증을 수행합니다. 탈퇴 시 프로필 사진의 Storage 객체와 공개 URL이 정리되는지 확인합니다.
6. 위 확인을 마친 뒤 앱 PR 병합/배포 승인을 받습니다. 앱에서는 경로를 공개 URL로 변환하고, 파일 상한 도달 시 미사용 파일 정리·재시도 기능을 검증해야 합니다.
7. 배포 후 앱에서 사진 탭, 선택 취소, 교체, 삭제, 재로그인, 공개 프로필/팔로우 목록 표시를 확인합니다.

DB만 적용한 상태를 기능 배포 완료로 보고하지 않습니다. 함수 배포가 실패하면 앱 배포를 진행하지 않습니다.
관리자/개인 계정 또는 service-role 키를 사용자 QA에 사용하지 않습니다.

## 장애 시 복구

- 우선 새 업로드 UI와 신규 INSERT 경로를 중지하고 현재 사진의 읽기·삭제 경로를 유지합니다.
- 앱을 이전 버전으로 되돌릴 때 이전 앱이 저장 경로를 URL로 오인하지 않는지 확인합니다. 기존 사진 데이터가 있으면 URL 변환 호환 코드를 유지합니다.
- DB 완전 롤백은 별도 데이터 변경 승인 대상입니다. 백업/영향 확인 후 프로필 참조를 null로 비우고, 실제 파일은 Storage API로 삭제합니다. 메타데이터 테이블 직접 DELETE는 하지 않습니다. 그 후 INSERT/SELECT/DELETE 정책과 RPC·private quota helper를 제거하고, `CHECK (profile_image_url IS NULL)` 제약을 복구합니다. 버킷은 비운 뒤 제거합니다.
- `delete-account`가 제거된 버킷을 참조하지 않게 함수 버전을 맞춥니다. migration history 삭제/repair로 변경을 숨기지 않고 별도 rollback migration을 작성합니다.

## 남은 앱·운영 작업

- #739: 상한(20개)에 도달한 계정의 미사용 파일 정리·재시도. 현재/타인 사진 및 다른 업로드 세션을 훼손하지 않는지 확인.
- #739: profileMapper/read/follow/notification 소비처 전체 점검. 알림에서 사진을 렌더링하지 않는 경우도 명시.
- 운영 후속: 프로필 사진 신고·관리자 삭제 기능은 별도 권한/UX 검토 항목입니다. 정지 사용자 업로드 차단이 관리자 삭제 기능을 대신하지 않습니다.
- 동시 업로드: 19개 상태에서 두 세션 INSERT를 동시에 실행해 최종 객체가 20개 이하인지 확인. 단일 bulk INSERT 테스트만으로 대체하지 않습니다.
