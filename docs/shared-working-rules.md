# OnePick 공용 작업 원칙

최종 갱신: 2026-10-02  
적용 대상: ChatGPT/Codex, Claude Code, OnePick 관련 모든 작업

이 문서는 사용자가 대화에서 확정한 **공통 작업 원칙 문서**다. 권한 순서는 아래 §1을 따르며, 사용자의 최신 지시와 `docs/pm/`의 현재 PM 기준 다음에 적용된다.  
ChatGPT/Codex와 Claude Code는 작업 시작 시 이 문서와 `docs/pm/`을 함께 확인한다.

## 1. 우선순위

과거 협의 내용과 이후 공유된 최신 문서의 내용이 다르면 **최신 문서의 내용을 따른다**.

충돌 시 기본 적용 순서는 다음과 같다.

1. 사용자가 가장 최근에 확정한 지시
2. 총괄 PM 운영 기준(`docs/pm/README.md`, `docs/pm/current-priorities.md`, #553)
3. 이 공용 작업 원칙 및 이후 갱신된 최신 공용 문서
4. 해당 작업의 최신 명세·디자인·PRD 문서
5. 기존 역할 분담·기술 문서
6. 과거 대화·이전 협의 내용

오래된 문서나 대화 기록을 근거로 최신 결정을 되돌리지 않는다.

### 총괄 PM 및 조직

2026-09-29부터 **ChatGPT가 OnePick 총괄 PM**을 맡는다. 공식 조직·우선순위·부서별 업무 기준은 `docs/pm/`에서 관리한다.

- `docs/pm/README.md`: PM 운영 원칙과 조직 구조
- `docs/pm/current-priorities.md`: 지금 무엇을 먼저 할지
- `docs/pm/current-status.md`: 현재 프로젝트 단계
- `docs/pm/departments/`: Product, UX, Engineering, Data/DB, QA/Security, Release/운영
- GitHub #553: 웹 PM 대시보드
- GitHub #296: 실제 owner/handoff 실행 상태

PM도 사용자의 최신 지시와 Production 승인 게이트를 우회할 수 없다.

## 2. 극초기 MVP 원칙

OnePick의 모든 작업은 **극초기 MVP 방향성**에 맞게 진행한다.

- 핵심 사용자 흐름과 실제 검증에 필요한 최소 범위를 우선한다.
- 비필수 기능, 과도한 구조화, 고도화, 확장 대비 설계는 후순위로 둔다.
- 비용·운영 복잡도·유지보수 부담을 늘리는 요소는 MVP 검증에 필수일 때만 채택한다.
- 기존 기획이나 구현이 이 원칙과 충돌하면, 최신 사용자 지시와 최신 문서를 기준으로 범위를 줄인다.
- “나중에 필요할 수 있음”만을 이유로 초기 MVP 범위를 넓히지 않는다.
- 초기 MVP에서 **AI 취향평가 UI·CTA는 노출하지 않는다.** 구현·데이터가 남아 있어도 최신 사용자 결정 전까지 화면에 다시 추가하지 않는다.

## 3. 현재 UI 안정화 단계 — 새 화면 추가 중단

2026-09-28 현재부터 별도 사용자 결정이 있기 전까지 **새 Figma 화면을 추가하지 않는다**.

우선순위는 새 화면 제작이 아니라 기존 화면을 다시 점검하고 Foundations 기준으로 디자인을 통일하는 것이다.

- 기존 화면을 먼저 검색·확인한다.
- 화면별로 유지(KEEP) / 수정(UPDATE) / 통합(MERGE) / 제거(DELETE)를 판단한다.
- 중복 화면을 새 번호로 다시 만들지 않는다.
- 디자인 통일 과정에서는 기능을 임의로 추가·삭제하지 않는다.
- 라우팅, 인증 의도, 딥링크, 입력 상태, 로딩/오류 상태, 저장 동작 등 기존 기능 계약을 유지한다.
- 기능 변경이 필요하면 디자인 통일 PR과 분리하고 사용자 결정을 먼저 받는다.

디자인 통일 우선순위:

1. 홈
2. 탐색
3. 원픽 등록
4. 개인/공개 프로필
5. 알림
6. 상품 상세
7. 설정 및 기타 화면

## 4. Figma 작업자 표기

Figma에서 Claude와 ChatGPT의 작업물을 구분할 수 있도록 **화면 번호 또는 제목 앞에 작업 주체를 명시**한다.

권장 형식:

- `지피티 75. 원픽 등록 v6`
- `클로드 76. 홈 v6`
- 또는 `[지피티] 75. ...`, `[클로드] 76. ...`

기존 화면 수정, 정리, 인계 시 동일하게 적용한다. 현재 UI 안정화 단계에서는 새 화면을 만들지 않는다.

## 5. Figma 중복 화면 처리

새로 만들려는 화면이 기존 화면과 중복되거나 유사하면 **바로 새로 만들거나 덮어쓰지 않는다**.

먼저 사용자에게 다음을 비교해 알린다.

- 기존 화면 번호·제목
- 새 작업안과 기존 화면의 차이
- 추가되는 요소
- 삭제되는 요소
- 변경되는 동작·문구·레이아웃

그 다음 처리한다.

- 사용자가 승인하면 기존 화면을 업데이트한다.
- 사용자가 승인하지 않으면 기존 화면을 그대로 존치한다.
- 승인 전에는 중복 화면을 임의로 새로 만들거나 기존 화면을 덮어쓰지 않는다.

현재 UI 안정화 단계에서는 이 원칙보다 더 엄격하게 **새 화면 생성 자체를 중단**하고 기존 화면만 정리한다.

## 6. 공개 프로필 / 78번 처리

Figma 78번은 별도의 “공유 프로필” 화면 체계로 유지하지 않는다.

- 공개 프로필은 기존 `/u/[username]` 화면을 기준으로 한다.
- 78번에서 유효한 흐름은 기존 공개 프로필에 통합한다.
- 2026-10-02 사용자 결정으로 **공개 프로필의 팔로우/팔로잉 관계 UI는 MVP에 포함**한다. 비로그인 팔로우 → 로그인 → 원래 프로필 복귀 → 1회 자동 팔로우(#491)를 실제 진입 흐름으로 사용한다.
- 노출 범위는 분리한다. 공개 프로필 Follow CTA는 켜되, 홈 팔로잉 전용 피드와 followee 원픽 변경 알림/설정·푸시는 별도 승인 전까지 노출하지 않는다.
- 팔로워/팔로잉 공개 수와 목록은 #645·#647의 안전한 조회 계약과 앱 구현을 완료한 뒤 노출한다.
- 별도 공유 프로필 화면, 중복 프로필 레이아웃, 별도 온보딩 유도 화면은 만들지 않는다.
- 78번 정리·삭제는 기존 공개 프로필에 필요한 동작이 반영됐는지 확인한 뒤 수행한다.

## 7. 원픽 등록 흐름 고정

매장/맛집 등록의 기본 순서는 다음으로 고정한다.

**상호명 검색 → 상호 선택/확정 → 메뉴명 입력·등록 → 상호 정보 + 입력한 메뉴명으로 AI 카테고리 추천 → 사용자 확인 → 이후 등록 단계**

세부 규칙:

- AI가 상호명만 보고 메뉴를 먼저 추천하는 흐름은 사용하지 않는다.
- 사용자가 먼저 상호를 찾고, 그 상호에 등록할 메뉴명을 직접 입력한다.
- 같은 메뉴명이 카탈로그에 정확히 있으면 기존 카테고리를 우선 활용할 수 있다.
- 일치가 없으면 기존 `suggest-item-categories`를 재사용해 **상호 정보 + 사용자가 입력한 메뉴명**으로 카테고리 후보를 추천한다.
- 추천은 사용자가 확인·변경할 수 있어야 한다.
- AI 실패·저신뢰 시 수동 카테고리 선택으로 폴백한다.
- 관리자 개입은 마지막 선택지다.
- 이 흐름을 위해 새 유료 API를 추가하지 않는다.

검색에 없는 매장 직접 등록 (2026-09-30 사용자 결정, #593):

- 등록 단계에서 맛집 **주소를 받지 않는다.** 카탈로그 검색 결과의 기존 주소·지역 표시는 지점 구분용으로 유지한다.
- 한 화면에 입력은 하나만 둔다. **상호명 → 네이버 지도 링크** 순서로 나누고, 둘 다 1 / 4 단계 안의 상태로 둔다.
- 네이버 지도 링크는 계속 필수다. 링크를 펼치는 외부 서비스·유료 API는 쓰지 않는다.
- "다시 검색하기" 버튼은 두지 않는다. 뒤로가기로 링크 → 상호명 → 검색 순서로 돌아간다.

## 8. 역할 분담

DB와 권한 변경은 작업 종류와 무관하게 기본적으로 **ChatGPT/Codex 담당**이다.

여기에는 Supabase DB 마이그레이션, 스키마·테이블·함수·트리거 변경, RLS, GRANT/REVOKE 등 권한 설정이 포함된다.

Claude는 해당 영역의 기본 구현자가 아니라 독립 리뷰·QA 역할을 맡는다. 사용자가 명시적으로 예외 위임한 경우만 직접 구현한다.

## 9. 적용 범위

이 원칙은 Figma뿐 아니라 앱 구현, DB, 관리자 화면, QA, 문서화, 자동화, 작업 인계에도 공통으로 적용한다.

세부 구현 규칙은 각 전문 문서(`docs/pm/`, `docs/design-foundations.md`, `docs/ai-role-division.md` 등)를 따르되, **이 문서 또는 이후의 최신 사용자 지시와 충돌하면 최신 기준을 우선**한다.

## 10. 문서 유지

이 대화에서 사용자가 새로운 공통 원칙을 확정하면 이 문서를 갱신한다.  
기존 결정을 바꾸는 내용은 예전 문장을 병렬로 남겨 혼동시키지 말고, 최신 결정을 기준으로 명확히 정리한다.
