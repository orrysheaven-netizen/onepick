# 검색 응답 속도 보완

## 확인한 지연 경로
- 기존 상품 검색: 마지막 입력 후 300ms 대기 → 카테고리 목록 요청 완료 대기 → search_items 요청 → 결과 표시.
- 기존 검색 RPC 자체가 상품 상태, 공개/선택 가능한 말단 카테고리와 상위 카테고리를 순위/개수 제한 전에 검사한다. 매번 보내던 카테고리 사전 조회는 중복이었다.
- 같은 검색어/범위의 최근 결과가 Query 캐시에 있어도 UI의 isWaiting이 다시 300ms 동안 이를 숨겼다.
- 검색 함수가 Query의 AbortSignal을 사용하지 않아 사용하지 않는 이전 검색의 클라이언트 요청을 중단하지 못했다.

## 변경
- 상품 검색의 입력 대기 설정을 300 → 150ms, 외부 영화 검색은 300 → 200ms로 조정한다. 모든 키 입력을 즉시 서버에 보내지 않으며 중간 입력의 타이머는 취소한다.
- ItemService.search는 기존 search_items RPC 한 번으로 조회한다. 전체 검색과 카테고리 검색 모두 중복 카테고리 왕복을 없앤다. 빈 검색은 요청하지 않는다.
- 서버 SQL, 결과 순위/별칭, 최대 20개 화면 결과, 공개 범위, 기존 인덱스는 바꾸지 않는다. 별도 검색 서비스나 대규모 카탈로그 다운로드를 추가하지 않는다.
- 정확히 같은 정규화 검색어와 범위의 최근 성공 결과만 입력 대기 없이 재사용한다. 신선도는 기존 설정과 같은 30초다. 만료·무효화·실패한 캐시는 빠른 경로에 사용하지 않으며 다른 검색어나 카테고리 결과를 임시로 대신 보여주지 않는다.
- 기존 사진/상품 수정의 items 캐시 무효화와 로그인 변경의 캐시 비우기를 유지한다. 검색어를 저장소나 분석 서버에 새로 기록하지 않는다.
- Query → 서비스 → 저장 계층 → Supabase HTTP 요청으로 AbortSignal을 전달한다. 검색어 변경/관찰 중단 시 이전 검색 응답 대기를 취소한다. 이미 서버에서 실행 중인 SQL/TMDB 작업까지 반드시 중단된다는 뜻은 아니다.
- 읽기 검색에만 취소를 적용한다. 영화 가져오기, 원픽 등록, 사진 저장 같은 쓰기 요청은 바꾸지 않는다. 외부 영화 검색의 2~60자 제한, 로그인 복귀, 요청 중복 방지와 오류 분류는 유지한다.

## 검증
- test-search-responsiveness.cjs: 실제 훅 소스의 대기값, 최신 입력, 정확한 범위별 캐시, 30초 만료/무효화/오류/빈 결과, 단일 검색 요청, signal 전달을 검사한다.
- 설치된 TanStack QueryObserver와 Supabase 클라이언트를 실제 사용하되 HTTP Fetch는 제어된 테스트 더블로 대체해 이전 검색 중단과 새 결과 격리를 검사한다. 외부 네트워크나 실제 사용자 데이터는 사용하지 않는다.
- 025_search_visibility.sql: 기존 RPC를 직접 익명/일반 사용자로 호출해 숨긴/닫힌/선택 불가 카테고리 및 상위 카테고리, 숨긴 상품/승인 대기, 단종 보존, 별칭, 첫 결과 제한, 빈 범위를 확인한다.
- 기존 상품 검색 테스트는 150ms 설정과 signal, 서버가 담당하는 카테고리 필터 계약으로 갱신한다. 영화 복구 테스트는 useQueryClient 모의 의존성만 추가하며 기존 검사를 유지한다.

## 측정 경계와 배포
- 150/200ms는 **입력 후 요청 시작 전 대기 설정**이지 전체 검색 완료 시간이나 실기기 실측값이 아니다. 확정 가능한 개선은 설정 대기 감소, 상품 검색당 순차 조회 2회 → 1회, 최근 동일 검색의 중복 요청 없음이다.
- 실제 속도는 배포 후 같은 휴대폰/네트워크에서 첫 검색·동일 검색·빠른 입력·외부 영화 검색의 p50/p95와 오류율을 비교해야 한다. 검색 결과 이미지 로딩 및 TMDB 첫 호출 지연까지 해결했다고 주장하지 않는다.
- 같은 PR #11과 작업 브랜치를 유지한다. main, Cloudflare/Vercel 배포, 운영 DB/마이그레이션/사용자 데이터, 인증 설정, 의존성을 변경하지 않는다. 운영 DB에는 검색 함수/인덱스/건수의 읽기 전용 확인만 수행했다.
